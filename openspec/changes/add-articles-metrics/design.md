## Контекст

Текущая кодовая база `article-service` (`kotlin-spring-realworld-example-app`) — одномодульное Spring Boot MVC + JPA приложение. Слой `web` содержит `*Handler`-классы (по факту `@RestController`), объединяющие HTTP-маршрутизацию с прямой работой через репозитории. Существующие маршруты статей используют префикс `/api`, ответы оборачиваются в JSON-envelope (`articles`, `article`, `comments`, `tags`, `errors`). Аутентификация — кастомный AOP-аспект `@ApiKeySecured` с JWT в `ThreadLocal`. Валидация идёт через `InvalidRequest.check(errors)` с HTTP 422 и формой `{"errors":{"field":["msg"]}}`.

Сущность `Article` уже хранит `createdAt: OffsetDateTime`. Репозиторий `ArticleRepository` расширяет `JpaSpecificationExecutor`, что даёт готовый механизм для динамических предикатов. Дата-фильтрация ранее не выносилась в отдельный метод, но в `ArticlesSpecifications.lastArticles` уже используется предикат по автору/тегу — это подтверждает, что предикаты по дате укладываются в существующий паттерн.

Изменение затрагивает только `article-service`, кросс-сервисных интеграций нет. ADRs в репозитории отсутствуют — ограничений со стороны принятых архитектурных решений нет.

## Цели / Нецелевое

**Цели:**
- Добавить read-only эндпоинт, возвращающий количество статей, `createdAt` которых попадает в `[from, to]`.
- Сохранить совместимость с текущим envelope-форматом, префиксом `/api`, форматом ISO-Z date-time и стеком MVC + JPA.
- Вынести подсчёт в слой `service`, оставив в `web` только маршрутизацию и маппинг envelope.

**ЗА РАМКАМИ:**
- Агрегации по авторам/тегам, временные ряды, экспорт отчётов.
- Изменение схемы БД и миграций (H2 in-memory, миграции не используются).
- Изменение механизма аутентификации и формы JWT-токена.
- Кэширование метрики (отдельный запрос с COUNT по индексу достаточен; `createdAt` не индексирован — см. риски).
- Новые эндпоинты для записи/изменения статей.

## Решения

### article-service

**1. Маршрут и envelope.**
- Новый маршрут: `GET /api/articles/metrics/count?from=<ISO>&to=<ISO>`.
- Ответ: `{"count": <long>}` в формате, согласованном с существующими envelope-ключами (новый ключ `count`, вложенность не вводится — значение скалярное).
- Маршрут кладётся в новый `MetricsHandler` в пакете `io.realworld.web` рядом с `ArticleHandler`. Это сохраняет границу «HTTP — в `web`», указанную в `04-engineering-standards.md §3`, и не размывает ответственность `ArticleHandler` (CRUD-операции).

**2. Аутентификация.**
- Аннотация `@ApiKeySecured(mandatory = false)`. Метрика публично-полезна и не зависит от авторства — optional-режим совместим с уже существующим паттерном для листинга статей (`GET /api/articles`).

**3. Сервисный слой.**
- Новый класс `MetricsService` в `io.realworld.service`. Принимает `ArticleRepository` через конструктор (constructor injection, без `@Autowired` на полях).
- Сигнатура: `fun countArticlesInPeriod(from: OffsetDateTime, to: OffsetDateTime): Long`.
- `@Transactional(readOnly = true)` на методе — фиксирует границу транзакции для JPA-запроса и соответствует правилу «multi-repository workflow → в сервис» (даже при одном репозитории это задаёт явную границу и предотвращает Lazy-loading за пределами транзакции, см. `04-engineering-standards.md §4.2`, §7.2).

**4. Запрос к БД.**
- Добавить derived-метод в `ArticleRepository`:
  ```kotlin
  fun countByCreatedAtBetween(from: OffsetDateTime, to: OffsetDateTime): Long
  ```
- **Альтернатива:** JPA Specification с `cb.between(root.get("createdAt"), from, to)`. Отклонена — derived-метод проще, дешевле поддерживать, и Hibernate генерирует чистый `COUNT(*)` без подгрузки сущностей.
- **Альтернатива:** `@Query("SELECT COUNT(a) FROM Article a WHERE a.createdAt BETWEEN :from AND :to")`. Отклонена — избыточна при наличии derived-метода.

**5. Парсинг и валидация параметров.**
- Принимать `from` и `to` как `String` (ISO-8601 с offset). Парсить в `OffsetDateTime` через `DateTimeFormatter.ISO_OFFSET_DATE_TIME`.
- Если `from` или `to` отсутствуют, либо `to < from` — формировать `InvalidRequest` с ошибками полей и отдавать HTTP 422 через существующий `InvalidRequestHandler` (см. `04-engineering-standards.md §5.3`, §5.4).
- Границы периода — inclusive, что соответствует сценарию «дата попадает в начальную или конечную дату периода» из spec.

**6. Нормализация часового пояса.**
- Парсинг сохраняет offset; для консистентности с существующими мапперами (`model.inout.Article`) — сериализация ответа не требуется (возвращается число), но `OffsetDateTime` на входе сравнивается «как есть» с `createdAt`, который уже хранится в UTC (`ZoneId.of("Z")`). Это исключает смешения TZ между клиентом и БД.

**7. Конструкторы и proxying.**
- `MetricsHandler` и `MetricsService` объявляются `class` (не `data class`), без `final`-модификаторов — Maven Kotlin plugin с `all-open` уже открывает их для Spring-прокси (см. `04-engineering-standards.md §4.1`). Это совместимо с `@ApiKeySecured` и `@Transactional`.

**8. Версионирование маршрута.**
- Используется существующий префикс `/api`, без `/v2` — это локальное расширение read-only API, не нарушающее обратной совместимости.

## Риски / Компромиссы

- **Отсутствие индекса по `createdAt`** — `COUNT(*)` будет full table scan → рост латентности при большом числе статей → добавить `@Index` на поле `createdAt` в `Article` (см. `04-engineering-standards.md §4.2` — индексы обязательны для полей, используемых в фильтрах). Т.к. миграций нет, изменение пересоздаст H2-схему; для прод-миграции потребуется отдельный шаг (см. P1 в `04-engineering-standards.md §12`).
- **Гонка между парсингом параметров и запросом** — минимальна (read-only), но при дрейфе часов сервера между `from`/`to` и `NOW()` возможна разница в одну секунду → задокументировать, что границы inclusive по серверному UTC, и не использовать «текущий момент» как границу.
- **H2-специфика** `countByCreatedAtBetween` проверена только на H2 → для прод-БД добавить интеграционный тест против целевого диалекта (`04-engineering-standards.md §9.1`).
- **Optional auth** означает, что анонимный клиент получит тот же `count`, что и аутентифицированный → метрика не содержит PII, но если потребуется ограничить доступ — повысить до `mandatory = true`.

## План миграции

- **БД:** миграция не требуется — H2 in-memory, схема управляется Hibernate, новые сущности/поля не вводятся (`04-engineering-standards.md §7.1`).
- **Деплой:** замена исполняемого JAR `article-service` (single module, см. `03-architecture.md §2`).
- **Откат:** повторный деплой предыдущего JAR; состояние в H2 утрачивается при рестарте, что соответствует текущему режиму (`04-engineering-standards.md §7.1`). Маршрут и обработчик удаляются вместе с кодом — внешних контрактов, которые требовалось бы сохранять, нет.
- **Совместимость:** только аддитивное расширение публичного API (`GET /api/articles/metrics/count`, новый ключ envelope `count`); существующие маршруты `/api/articles*`, формат `articlesCount`, JWT-контракт и CORS не затрагиваются (`04-engineering-standards.md §5.1`, §5.2).
- **Верификация после применения:** `./mvnw test` (см. `04-engineering-standards.md §2.3`) + ручной сценарий: запрос с известным диапазоном, содержащим ровно одну статью (граница inclusive), и запрос с пустым диапазоном (ожидаемый `count = 0`).

## Открытые вопросы

- **Индекс по `Article.createdAt`.** Решение о добавлении `@Index` отложить до этапа применения при наличии данных о реальных объёмах; для H2 достаточно derived-метода, но для production-БД индекс обязателен (`04-engineering-standards.md §4.2`, §7.3).
- **Required auth для метрик.** По умолчанию — optional (`@ApiKeySecured(mandatory = false)`); если заказчик сочтёт объёмы чувствительными — перевод на `mandatory = true` отдельным изменением с покрытием тестами 401/403 (`04-engineering-standards.md §5.4`, §9.1).
- **Форма ошибки при `to < from`.** Текущее решение — HTTP 422 с полем `errors.range` через существующий `InvalidRequestHandler`; уточнить с клиентом, не требуется ли отдельный код (например, 400) для семантически некорректного диапазона.
- **Кросс-сервисный доступ к метрикам.** В текущем proposal отсутствует; при появлении потребителей в `service1` или `spring-school` потребуется отдельный сервисный маршрут и ADR на cross-service контракт (см. `08-services.md`).
- **ADR.** Папка `adr/` в репозитории отсутствует, принятых долгосрочных архитектурных обязательств это изменение не устанавливает — `adr`-шаг schema `spec-driven-with-adr` завершится без создания новых файлов под `adr/`.
